# Frontend Optimization

Оптимизация Frontend-приложений — это комплекс методов, позволяющих уменьшить время загрузки приложения, сократить объем передаваемых данных, ускорить выполнение JavaScript и сделать интерфейс более отзывчивым.

Условно оптимизацию можно разделить на несколько направлений.

## Сетевые оптимизации

Основная задача — уменьшить объем передаваемых данных и ускорить их доставку пользователю.

### Сборка приложения

Современные приложения собираются с помощью Vite, Webpack, Rollup и других сборщиков.

Сборщики позволяют:

- объединять файлы в bundle;
- удалять неиспользуемый код (Tree Shaking);
- минифицировать JavaScript и CSS;
- разбивать приложение на чанки (Code Splitting).

### Code Splitting

Code Splitting позволяет не загружать весь JavaScript сразу.

Приложение разбивается на независимые части (chunks), которые загружаются только при необходимости.

Чаще всего отдельно загружают:

- страницы;
- тяжелые компоненты;
- административную часть приложения;
- редакторы;
- графики;
- карты.

В React для этого обычно используют `React.lazy()` и `Suspense`.

### Lazy Loading

Lazy Loading позволяет откладывать загрузку ресурсов до момента, когда они действительно понадобятся.

Чаще всего лениво загружают:

- изображения;
- видео;
- шрифты;
- компоненты.

Это позволяет быстрее отобразить критически важный контент.

### CDN

Статические ресурсы (JavaScript, CSS, изображения, шрифты) часто размещают на CDN.

Контент отдается с ближайшего к пользователю сервера, что уменьшает задержку сети и ускоряет загрузку.

### Долгоживущее кеширование

При каждом деплое желательно повторно загружать только изменившиеся файлы.

Для этого обычно используют **content hash** в имени файла.

### Пример

```text
app.a3fd81.js
vendor.4bc921.js
```

Если изменился только код приложения, браузер продолжит использовать закешированный `vendor` bundle.

### HTTP/2 и HTTP/3

В HTTP/1.1 большое количество файлов приводило к ухудшению производительности из-за ограниченного числа параллельных соединений.

В HTTP/2 и HTTP/3 эта проблема значительно уменьшилась благодаря мультиплексированию запросов.

Тем не менее чрезмерное количество маленьких чанков также может негативно влиять на производительность.

## Кеширование

Правильное кеширование значительно уменьшает количество сетевых запросов.

### HTTP Cache

Браузер может повторно использовать ранее загруженные ресурсы без обращения к серверу.

Основные механизмы:

- `Cache-Control`;
- `ETag`;
- `Last-Modified`.

### Service Worker

Service Worker позволяет реализовать офлайн-режим работы приложения.

Он может:

- кешировать ресурсы;
- перехватывать запросы;
- отдавать данные без обращения к серверу;
- реализовывать стратегию **Offline First**.

### Кеширование данных

После получения данных не всегда требуется повторно обращаться к серверу.

Библиотеки вроде React Query и RTK Query автоматически кешируют ответы API и повторно используют их между компонентами.

### Локальное хранение

Для хранения данных в браузере можно использовать:

- `localStorage`;
- `sessionStorage`;
- `IndexedDB`.

`IndexedDB` обычно используют для хранения больших объемов данных или реализации офлайн-режима.

## Оптимизация React

Большинство проблем производительности React связано с лишними ререндерами, а не с самим DOM.

Основные способы оптимизации:

- корректное использование `key`;
- `React.memo`;
- `useMemo`;
- `useCallback`;
- разделение компонентов;
- минимизация состояния;
- ленивый импорт компонентов;
- `Suspense`;
- `useTransition` для некритичных обновлений интерфейса.

Важно понимать, что мемоизация тоже имеет стоимость.

Если вычисление дешевле проверки зависимостей, использование `useMemo` или `useCallback` может только ухудшить производительность.

## Оптимизация алгоритмов

Даже хорошо оптимизированный React не компенсирует неэффективные алгоритмы.

Важно учитывать:

- временную сложность (Big O);
- пространственную сложность;
- стоимость поиска;
- стоимость сортировки;
- стоимость копирования объектов и массивов.

Во многих случаях изменение алгоритма дает больший прирост производительности, чем микрооптимизации.

## Работа с DOM

Изменение DOM — одна из самых дорогих операций в браузере.

Основные рекомендации:

- минимизировать количество изменений DOM;
- уменьшать количество Forced Layout;
- по возможности группировать изменения;
- использовать виртуализацию больших списков;
- использовать `passive` listeners для `scroll` и `touch`;
- избегать частых вызовов:
  - `getBoundingClientRect()`;
  - `offsetWidth`;
  - `clientWidth`;
  - `scrollHeight`.

Для анимаций предпочтительно изменять `transform` и `opacity`, поскольку они обычно не вызывают Layout и могут обрабатываться на этапе Composition.

## Оптимизация изображений

Изображения часто становятся основной причиной медленной загрузки страниц.

Рекомендуется:

- использовать современные форматы (`WebP`, `AVIF`);
- использовать адаптивные изображения (`srcset`, `sizes`);
- задавать `width` и `height`, чтобы избежать Layout Shift;
- использовать Lazy Loading;
- не загружать изображения большего размера, чем требуется устройству пользователя.

## Оптимизация JavaScript

Длительное выполнение JavaScript блокирует главный поток браузера.

Для уменьшения нагрузки рекомендуется:

- использовать `debounce`;
- использовать `throttle`;
- разбивать тяжелые вычисления на части;
- переносить длительные вычисления в `Web Worker`;
- избегать долгих синхронных операций.

Если JavaScript выполняется десятки или сотни миллисекунд, пользовательский интерфейс перестает реагировать до завершения выполнения кода.

## Инструменты профилирования

Оптимизация должна основываться на измерениях, а не предположениях.

Чаще всего используют:

- Chrome DevTools (Performance);
- Chrome DevTools (Memory);
- Lighthouse;
- React DevTools Profiler;
- Web Vitals.

## Частые ошибки

❌ Использовать мемоизацию без необходимости.

Каждая мемоизация тоже требует вычислений и хранения данных.

❌ Делить приложение на слишком большое количество маленьких чанков.

Это увеличивает количество сетевых запросов и может ухудшить производительность.

❌ Выполнять тяжелые вычисления в главном потоке.

Это блокирует интерфейс и ухудшает пользовательский опыт.

❌ Постоянно читать размеры элементов после изменения DOM.

Это может привести к Forced Layout и дополнительным перерасчетам страницы.

❌ Использовать большие изображения для мобильных устройств.

Передаваемый объем данных должен соответствовать размеру экрана.

❌ Использовать `will-change` без необходимости.

Создание большого количества compositor layers также требует ресурсов браузера.
