# Critical Rendering Path

Critical Rendering Path (критический путь рендеринга) — это последовательность этапов, которые проходит браузер от получения HTML до отображения готовой страницы на экране.

Понимание этого процесса помогает объяснить причины медленной загрузки страницы, блокировки рендера и появления Layout Shift.

## Получение HTML

После обращения к серверу браузер получает HTML-документ.

По сути HTML представляет собой обычный текст, который браузеру необходимо распарсить и преобразовать во внутренние структуры данных.

## Построение DOM

Браузер начинает последовательно читать HTML сверху вниз.

Во время парсинга создается **DOM (Document Object Model)** — дерево объектов, представляющее структуру HTML-документа.

Каждый HTML-тег становится отдельным объектом со своими свойствами и методами.

Парсинг DOM происходит постепенно по мере чтения HTML.

## Загрузка внешних ресурсов

Во время парсинга браузер встречает ссылки на внешние ресурсы:

- CSS (`<link>`);
- JavaScript (`<script>`);
- изображения (`<img>`);
- шрифты (`@font-face`);
- видео;
- другие ресурсы.

После обнаружения браузер начинает их загрузку.

Поведение зависит от типа ресурса.

## Загрузка JavaScript

Обычные `<script>` могут приостанавливать парсинг HTML, поскольку JavaScript способен изменять структуру DOM.

### Обычный script

```html
<script src="app.js"></script>
```

Порядок выполнения:

1. парсер останавливается;
2. начинается загрузка файла;
3. после загрузки скрипт сразу выполняется;
4. парсинг HTML продолжается.

Такие скрипты называют **parser-blocking**.

### Async

```html
<script async src="analytics.js"></script>
```

Особенности:

- загрузка происходит параллельно с парсингом HTML;
- после завершения загрузки парсер приостанавливается;
- скрипт выполняется сразу после загрузки;
- затем парсинг продолжается.

Порядок выполнения нескольких `async`-скриптов не гарантируется.

Первым выполнится тот, который загрузился раньше.

Поэтому `async` плохо подходит для зависимых скриптов.

Кроме того, если `async` выполнится до построения нужного DOM-элемента, вызов `querySelector()` может вернуть `null`.

### Defer

```html
<script defer src="app.js"></script>
```

Особенности:

- загрузка происходит параллельно с парсингом HTML;
- парсер не блокируется;
- выполнение откладывается до полного построения DOM;
- порядок выполнения нескольких `defer`-скриптов сохраняется.

Именно поэтому `defer` обычно используют для основного JavaScript приложения.

К моменту выполнения `defer` весь DOM уже построен.

### DOMContentLoaded

Событие `DOMContentLoaded` происходит только после:

1. полного парсинга HTML;
2. выполнения всех `defer`-скриптов.

`async`-скрипты с этим событием не синхронизируются.

## Загрузка CSS

CSS загружается параллельно с построением DOM.

Сам по себе CSS не блокирует парсинг HTML.

Однако если браузер встречает обычный `<script>`, а ранее обнаруженные CSS-файлы еще не успели загрузиться, выполнение JavaScript откладывается до окончания загрузки стилей.

Это необходимо потому, что JavaScript может получать вычисленные стили и размеры элементов (`getComputedStyle()`, `getBoundingClientRect()` и другие API), которые зависят от примененного CSS.

## Построение CSSOM

После загрузки CSS браузер строит **CSSOM (CSS Object Model)** — дерево всех CSS-правил.

CSSOM используется для вычисления итоговых стилей каждого элемента.

## Построение Render Tree

Когда готовы DOM и CSSOM, браузер объединяет их в **Render Tree**.

В Render Tree попадают только отображаемые элементы.

Например:

- элементы с `display: none` не входят в Render Tree;
- псевдоэлементы (`::before`, `::after`) входят в Render Tree.

Пока CSSOM не построен, Render Tree создать невозможно.

Именно поэтому браузер старается не отображать страницу до загрузки критических CSS-файлов, чтобы избежать появления неоформленного контента (**FOUC — Flash of Unstyled Content**).

## Layout (Reflow)

После построения Render Tree браузер вычисляет геометрию страницы.

Для каждого элемента определяются:

- ширина;
- высота;
- координаты;
- положение относительно других элементов.

Этот этап называется **Layout** или **Reflow**.

## Paint

После вычисления геометрии браузер отрисовывает содержимое каждого элемента.

На этом этапе рисуются:

- текст;
- фон;
- изображения;
- границы;
- тени;
- градиенты;
- другие визуальные свойства.

## Composition

На последнем этапе браузер объединяет подготовленные слои в итоговое изображение и выводит его на экран.

Часть этой работы обычно выполняется видеокартой.

Если элемент находится на отдельном compositor layer, браузеру часто достаточно выполнить только Composition без повторного Layout и Paint.

Именно поэтому анимации `transform` и `opacity` считаются наиболее производительными.

## Оптимизация

Для ускорения загрузки страницы рекомендуется:

- использовать `defer` для основного JavaScript;
- минимизировать количество блокирующих ресурсов;
- загружать только критический CSS;
- использовать lazy loading для изображений;
- указывать `width` и `height` для изображений, чтобы избежать Layout Shift;
- использовать современные форматы изображений (`WebP`, `AVIF`);
- по возможности анимировать `transform` и `opacity` вместо свойств, изменяющих геометрию элементов.

## Частые ошибки

❌ Считать, что CSS блокирует парсинг HTML.

CSS не блокирует парсер, но может задерживать выполнение обычных `<script>`.

❌ Думать, что `async` сохраняет порядок выполнения скриптов.

`async`-скрипты выполняются по мере завершения загрузки.

❌ Считать, что DOM и Render Tree — одно и то же.

DOM содержит структуру документа, а Render Tree — только отображаемые элементы с вычисленными стилями.

❌ Полагать, что `DOMContentLoaded` срабатывает сразу после построения DOM.

Событие ожидает завершения выполнения всех `defer`-скриптов.

❌ Не указывать размеры изображений.

Это может привести к Layout Shift и ухудшению пользовательского опыта.
