# SSR и Server Components

## Зачем понадобился SSR

Изначально React работал по модели **Client-Side Rendering (CSR)**.

Сервер практически ничего не знал о приложении и отдавал пользователю минимальный HTML:

```html
<body>
  <div id="root"></div>

  <script src="bundle.js"></script>
</body>
```

После загрузки страницы браузер:

1. скачивал JavaScript;
2. выполнял его;
3. создавал Virtual DOM;
4. строил DOM;
5. отображал интерфейс.

Схематично процесс выглядит так:

```text
Запрос

↓

HTML

↓

Загрузка JS

↓

Выполнение JS

↓

React Render

↓

Появилась страница
```

### Преимущества CSR

- простая архитектура;
- минимальная нагрузка на сервер;
- удобно разрабатывать SPA.

### Недостатки CSR

- долгое первое отображение страницы;
- большой объем JavaScript;
- пользователь некоторое время видит пустой экран;
- исторически были проблемы с SEO (сегодня большинство поисковых систем умеют выполнять JavaScript, но SSR по-прежнему остается предпочтительным для SEO).

Именно эти недостатки привели к появлению серверного рендеринга.

## CSR (Client-Side Rendering)

При CSR HTML содержит лишь контейнер для будущего приложения.

Вся работа происходит в браузере.

```text
Server

↓

HTML

↓

Browser

↓

React

↓

DOM
```

Практически все вычисления выполняются на стороне клиента.

## SSR (Server-Side Rendering)

При SSR сервер самостоятельно запускает React и заранее генерирует HTML.

```text
Request

↓

Server

↓

React Render

↓

Готовый HTML

↓

Browser
```

Пользователь получает уже готовую страницу и видит контент значительно быстрее.

Однако сразу после получения HTML страница еще не является интерактивной.

Обработчики событий пока не подключены, поэтому браузеру необходимо загрузить JavaScript.

## Hydration

**Hydration** — процесс "оживления" HTML, полученного от сервера.

Во время Hydration React:

- строит Virtual DOM;
- сравнивает его с существующим DOM;
- подключает обработчики событий;
- восстанавливает состояние приложения.

```text
Server

↓

HTML

↓

Browser

↓

Hydration

↓

Интерактивная страница
```

> **Важно:** React не создает DOM заново. Он использует уже существующие элементы.

Если HTML, полученный с сервера, отличается от того, который React ожидает получить на клиенте, возникают **Hydration Errors**.

Типичные причины:

- `Date.now()`;
- `Math.random()`;
- чтение `window` или `localStorage` во время SSR;
- различия во времени, локали или данных между сервером и клиентом.

## SSG (Static Site Generation)

При SSG страницы генерируются заранее во время сборки проекта.

```text
Build

↓

HTML

↓

CDN

↓

User
```

### Преимущества

- очень быстрый первый рендер;
- практически отсутствует нагрузка на сервер;
- отлично подходит для SEO;
- хорошо кэшируется.

### Недостатки

После изменения контента обычно требуется новая сборка проекта.

### Подходит для

- документации;
- блогов;
- лендингов;
- маркетинговых страниц.

## ISR (Incremental Static Regeneration)

ISR решает главный недостаток SSG.

Страница остается статической, но может автоматически пересобираться через заданный интервал.

Например:

```ts
revalidate = 60;
```

означает, что сервер сможет пересоздать страницу не чаще одного раза в минуту.

```text
User

↓

Получает старую версию страницы

↓

Server

↓

Фоновая генерация новой версии

↓

Следующие пользователи получают обновленный HTML
```

Таким образом сочетаются преимущества SSG и SSR.

## Streaming SSR

В классическом SSR сервер сначала полностью рендерит страницу, а затем отправляет ее клиенту.

```text
Render

↓

HTML

↓

Отправка
```

Если страница большая, пользователь долго ничего не видит.

Streaming SSR позволяет отправлять HTML по частям.

```text
Header

↓

Sidebar

↓

Content

↓

Comments
```

Пользователь начинает видеть интерфейс значительно раньше.

Streaming SSR особенно хорошо сочетается с `Suspense`.

## React Server Components (RSC)

**React Server Components** позволяют выполнять часть компонентов полностью на сервере.

Если компонент:

- получает данные;
- не использует состояние;
- не использует эффекты;
- не использует браузерные API;
- не содержит обработчиков событий,

то его можно выполнить исключительно на сервере.

```text
Database

↓

Server Component

↓

HTML

↓

Browser
```

Такой компонент:

- не попадает в клиентский JavaScript;
- уменьшает размер бандла;
- ускоряет Hydration.

### Ограничения Server Components

Нельзя использовать:

- `useState`;
- `useEffect`;
- `useRef`;
- обработчики событий (`onClick` и др.);
- `window`;
- `document`.

Если компоненту нужна интерактивность, используется **Client Component**.

## `"use client"`

По умолчанию Server Components выполняются только на сервере.

Если компонент должен работать в браузере, в начале файла указывается директива:

```tsx
"use client";
```

После этого компонент становится обычным клиентским React-компонентом.

## Как работают Server Components

Упрощенная схема:

```text
Database

↓

Server Component

↓

RSC Payload

↓

Browser

↓

Client Components

↓

Hydration
```

Помимо HTML сервер отправляет специальный **RSC Payload**, содержащий описание дерева серверных компонентов и мест подключения клиентских компонентов.

## Сравнение способов рендеринга

| Подход  | Где рендерится HTML                                        | Когда генерируется                    | Когда появляется интерактивность |
| ------- | ---------------------------------------------------------- | ------------------------------------- | -------------------------------- |
| **CSR** | В браузере                                                 | После загрузки JavaScript             | Сразу после рендера React        |
| **SSR** | На сервере                                                 | На каждый запрос                      | После Hydration                  |
| **SSG** | На сервере                                                 | Во время сборки                       | После Hydration                  |
| **ISR** | На сервере                                                 | Во время сборки + фоновая регенерация | После Hydration                  |
| **RSC** | Серверные компоненты — на сервере, клиентские — в браузере | Во время запроса или сборки           | Только Client Components         |

## Что выбрать

- **CSR** — SPA, CRM, админки, личные кабинеты.
- **SSR** — интернет-магазины, новостные сайты, проекты с SEO и динамическими данными.
- **SSG** — документация, лендинги, корпоративные сайты, блоги.
- **ISR** — каталоги, маркетплейсы, сайты с периодически обновляемыми данными.
- **RSC** — современные приложения на Next.js с разделением серверной и клиентской логики.

## Как все связано

```text
React Rendering

                     CSR
                      │
        ┌─────────────┴─────────────┐
        │                           │
       SSR                        SSG
        │                           │
        └─────────────┬─────────────┘
                      │
                     ISR
                      │
               Streaming SSR
                      │
          React Server Components
                      │
                 Hydration
```

## Частые ошибки

❌ Считать, что SSR делает страницу сразу интерактивной.

После получения HTML браузеру необходимо выполнить **Hydration**.

❌ Думать, что Hydration создает DOM заново.

React использует уже существующий DOM и лишь подключает к нему логику.

❌ Использовать `window`, `document`, `Date.now()` или `Math.random()` во время SSR.

Это может привести к ошибкам Hydration.

❌ Считать, что Server Components полностью заменяют Client Components.

Server Components не поддерживают состояние, эффекты и обработчики событий.

❌ Думать, что RSC и SSR — одно и то же.

SSR определяет **где рендерится HTML**, а RSC определяет **где выполняется компонент**. Эти технологии могут использоваться вместе.
