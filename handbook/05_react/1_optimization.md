# Оптимизация React

Оптимизация React — это не только использование `React.memo` или `useMemo`. На практике она включает несколько направлений:

- уменьшение объема отображаемых элементов;
- уменьшение объема загружаемого JavaScript;
- снижение приоритета некритичных обновлений;
- объединение нескольких обновлений;
- принудительное выполнение обновления в особых случаях.

## Virtualization

**Virtualization (виртуализация списков)** — это техника, при которой React рендерит только видимую часть большого списка, а не все элементы сразу.

Например, если таблица содержит 100 000 строк, пользователю одновременно видно лишь около 40.

Вместо создания всех 100 000 DOM-узлов React создает только видимые элементы и переиспользует их во время прокрутки.

```
100 000 элементов

↓

видно только 40

↓

DOM содержит только 40 элементов
```

### Преимущества

- значительно меньше DOM-узлов;
- быстрее рендер;
- меньше потребление памяти;
- плавный скролл.

### Популярные библиотеки

- `react-window`;
- `react-virtualized`;
- `@tanstack/react-virtual`.

## Code Splitting

По умолчанию сборщик объединяет приложение в несколько JavaScript-бандлов.

Чем больше размер начального бандла, тем дольше пользователь ждет загрузку приложения.

**Code Splitting** позволяет разбить приложение на независимые чанки и загружать их только при необходимости.

Например:

```
Главная страница

↓

Загрузился только Home.js

↓

Переход в Dashboard

↓

Загрузился Dashboard.js
```

В React ленивую загрузку компонентов обычно реализуют через `React.lazy()`:

```tsx
const Dashboard = React.lazy(() => import("./Dashboard"));
```

## Suspense

`Suspense` позволяет отображать запасной интерфейс (`fallback`), пока React ожидает завершения асинхронной операции.

Чаще всего используется совместно с:

- `React.lazy`;
- Server Components;
- современными механизмами загрузки данных.

```tsx
<Suspense fallback={<Spinner />}>
  <Dashboard />
</Suspense>
```

Пока компонент загружается, пользователь увидит `Spinner`.

После завершения загрузки React автоматически заменит его на настоящий компонент.

> **Важно:** `Suspense` сам ничего не загружает. Он только ожидает завершения асинхронной операции и отображает запасной интерфейс.

## useTransition

Иногда действие пользователя вызывает тяжелое обновление интерфейса.

Например:

```
Печать в input

↓

Фильтрация 20 000 строк

↓

Интерфейс начинает тормозить
```

`useTransition` позволяет пометить часть обновлений как менее приоритетные.

```tsx
startTransition(() => {
  setFilteredData(...);
});
```

React сначала выполнит критичные обновления (например, изменение текста в `input`), а тяжелую работу выполнит позже.

Интерфейс останется отзывчивым.

> **Важно:** `useTransition` ничего не ускоряет. Он только изменяет приоритет выполнения обновлений.

## useDeferredValue

`useDeferredValue` похож на `useTransition`, но работает иначе.

Он не откладывает изменение состояния, а откладывает использование уже обновленного значения.

```tsx
const deferredSearch = useDeferredValue(search);
```

Например, пользователь быстро вводит текст:

```
a

ab

abc

abcd
```

Поле ввода обновляется мгновенно.

Список продолжает некоторое время использовать старое значение, а затем автоматически обновляется.

```
Input

↓

быстро

↓

List

↓

немного позже
```

### Различие

**useTransition**

- откладывает обновление состояния.

**useDeferredValue**

- откладывает использование уже обновленного значения.

## Automatic Batching

До React 18 несколько обновлений объединялись только внутри обработчиков событий React.

Например:

```tsx
setA(1);
setB(2);
```

приводило к одному ререндеру.

Однако внутри `setTimeout()` или `Promise` происходило несколько отдельных ререндеров.

Начиная с React 18 batching работает практически везде:

- `Promise.then()`;
- `fetch()`;
- `setTimeout()`.

```
setA()

↓

setB()

↓

setC()

↓

Один Render
```

Это уменьшает количество лишних ререндеров и повышает производительность приложения.

## flushSync

Иногда требуется выполнить обновление немедленно, не дожидаясь окончания batching.

Для этого используют `flushSync`.

```tsx
flushSync(() => {
  setOpen(true);
});
```

После выхода из `flushSync` DOM уже гарантированно обновлен.

Это позволяет безопасно измерять размеры элементов или выполнять интеграцию со сторонними библиотеками.

Например:

```tsx
element.getBoundingClientRect();
```

> **Важно:** использовать `flushSync` рекомендуется только в исключительных случаях. Он отключает преимущества конкурентного рендеринга и может ухудшить производительность.

## Как связаны React.lazy и Suspense

Эти механизмы работают совместно, но решают разные задачи.

```
React.lazy

↓

загружает компонент

↓

Suspense

↓

ожидает завершения загрузки

↓

показывает fallback

↓

отображает готовый компонент
```

- `React.lazy` отвечает за ленивую загрузку компонентов.
- `Suspense` отвечает за отображение запасного интерфейса во время ожидания.

## Как useTransition связан с Scheduler

После вызова `startTransition()` React помечает обновление как менее приоритетное.

Далее Scheduler может:

- выполнить его позже;
- прервать выполнение;
- уступить управление браузеру;
- продолжить работу позже.

Именно благодаря архитектуре Fiber и Scheduler `useTransition` позволяет сохранять отзывчивость интерфейса.

## Практические рекомендации

- Используйте **Virtualization** для длинных списков (тысячи элементов).
- Применяйте **Code Splitting** для редко используемых разделов приложения.
- Используйте **Suspense** для отображения состояния загрузки ленивых компонентов.
- Применяйте **useTransition** и **useDeferredValue** в интерфейсах с тяжелыми вычислениями (поиск, фильтрация, сортировка, большие таблицы).
- **Automatic Batching** работает автоматически — использовать его вручную не требуется.
- **flushSync** применяйте только тогда, когда действительно необходимо немедленно получить обновленный DOM.

## Частые ошибки

❌ Считать, что `useMemo` и `React.memo` — универсальные средства оптимизации.

Оптимизация должна основываться на профилировании. Лишняя мемоизация может только ухудшить производительность.

❌ Использовать Virtualization для небольших списков.

Дополнительная сложность не всегда оправдана.

❌ Думать, что `Suspense` загружает компоненты.

Он только отображает запасной интерфейс во время ожидания.

❌ Считать, что `useTransition` делает вычисления быстрее.

Он лишь снижает приоритет обновлений, сохраняя отзывчивость интерфейса.

❌ Использовать `flushSync` без необходимости.

Это отключает преимущества конкурентного рендеринга и может негативно сказаться на производительности.
