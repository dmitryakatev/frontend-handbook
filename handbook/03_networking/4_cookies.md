# Cookies

Cookies — это механизм хранения небольшого объема данных, позволяющий серверу и браузеру сохранять состояние между HTTP-запросами.

Сам HTTP является **stateless**, поэтому каждый запрос обрабатывается независимо.

Cookies позволяют связать несколько запросов одного пользователя в единую сессию.

## Для чего используются Cookies

На практике Cookies чаще всего используют для хранения:

- идентификатора пользовательской сессии;
- Refresh Token;
- пользовательских настроек;
- языковых предпочтений;
- данных A/B-тестов;
- антибот-защиты;
- аналитической информации.

Несмотря на то что в Cookies можно хранить любые небольшие данные, для хранения большого объема информации обычно используют `localStorage` или `IndexedDB`.

## Как работают Cookies

Cookie можно установить двумя способами.

### Через сервер

Наиболее распространенный вариант.

Сервер отправляет заголовок:

```http
Set-Cookie: sessionId=abc123
```

После этого браузер автоматически сохраняет Cookie.

### Через JavaScript

Cookie также можно создать на стороне клиента:

```js
document.cookie = "theme=dark";
```

Однако таким способом нельзя установить некоторые защитные атрибуты, например `HttpOnly`.

## Как Cookies отправляются на сервер

После сохранения браузер автоматически прикрепляет Cookie ко всем подходящим HTTP-запросам.

Например:

```http
Cookie: sessionId=abc123
```

При этом браузер отправляет не все Cookies, а только те, которые соответствуют условиям:

- Domain;
- Path;
- Secure;
- SameSite.

## Ограничения

Cookies имеют ряд ограничений:

- размер одной Cookie — около **4 КБ**;
- количество Cookies на один домен ограничено (зависит от браузера).

Поэтому Cookies не подходят для хранения больших объемов данных.

## Атрибуты Cookies

### Expires и Max-Age

Определяют срок жизни Cookie.

**Expires** задает конкретную дату удаления.

```http
Expires=Wed, 21 Oct 2026 07:28:00 GMT
```

**Max-Age** задает время жизни в секундах.

```http
Max-Age=3600
```

Если указаны оба атрибута, приоритет обычно имеет `Max-Age`.

### Domain

Определяет домен, для которого будет отправляться Cookie.

```http
Domain=example.com
```

Такая Cookie будет доступна и поддоменам.

Например:

- `api.example.com`;
- `app.example.com`.

### Path

Определяет путь, при котором Cookie автоматически прикрепляется к запросу.

```http
Path=/auth
```

Такая Cookie будет отправляться только при обращении к маршрутам внутри `/auth`.

Это часто используют, например, для хранения Refresh Token.

### Secure

При наличии атрибута `Secure` Cookie передается только по HTTPS.

По HTTP такая Cookie никогда не отправляется.

### HttpOnly

`HttpOnly` — один из важнейших атрибутов безопасности.

Если он установлен, JavaScript не сможет получить доступ к Cookie через `document.cookie`.

При этом браузер продолжит автоматически отправлять такую Cookie серверу.

Именно поэтому Refresh Token обычно рекомендуют хранить в `HttpOnly Cookie`.

## SameSite

Атрибут `SameSite` определяет, в каких межсайтовых сценариях браузер имеет право автоматически прикреплять Cookie к запросу.

Основная задача `SameSite` — защита от **CSRF-атак**.

Поддерживаются три режима.

### SameSite=Strict

Самый строгий режим.

Cookie отправляется только при запросах, инициированных с того же сайта.

Например:

```text
google.com
      ↓
bank.com
```

При таком переходе Cookie банка отправлена не будет.

Это обеспечивает максимальную защиту от CSRF, но может ухудшать пользовательский опыт.

### SameSite=Lax

Используется по умолчанию в современных браузерах.

Cookie отправляется:

- при навигации внутри сайта;
- при переходе по обычной ссылке;
- при открытии сайта из закладки;
- при вводе адреса вручную;
- при переходе из поисковой системы.

Однако при фоновых межсайтовых запросах Cookie уже не прикрепляется.

Например:

```js
fetch("https://bank.com/api");
```

или

```js
xhr.send(...);
```

Именно это защищает большинство приложений от классических CSRF-атак.

### SameSite=None

Cookie разрешено отправлять во всех сценариях, включая кросс-сайтовые запросы.

Однако этого недостаточно для работы `fetch` или `XMLHttpRequest`.

Для AJAX-запросов дополнительно требуется корректная настройка CORS.

На клиенте:

```js
fetch(url, {
  credentials: "include",
});
```

или

```js
xhr.withCredentials = true;
```

На сервере:

```http
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://app.example.com
```

Использовать

```http
Access-Control-Allow-Origin: *
```

вместе с

```http
Access-Control-Allow-Credentials: true
```

нельзя.

Кроме того, Cookie с `SameSite=None` обязательно должна иметь атрибут `Secure`, иначе современные браузеры не сохранят ее.

## SameSite и credentials

Важно понимать, что `SameSite` и `credentials` — это разные механизмы.

Сначала браузер проверяет `SameSite`:

> Разрешено ли этой Cookie участвовать в данном типе запроса?

Если ответ отрицательный, Cookie не будет отправлена.

Затем браузер проверяет настройки CORS и `credentials`.

Если для `fetch` не указано:

```js
credentials: "include";
```

то Cookie также не будет отправлена.

## Поведение SameSite

| Сценарий                                                                               | Strict | Lax | None |
| -------------------------------------------------------------------------------------- | :----: | :-: | :--: |
| **Переходы**                                                                           |        |     |      |
| Переход по ссылке внутри того же сайта                                                 |   ✅   | ✅  |  ✅  |
| Прямой переход (URL в адресной строке, закладки)                                       |   ✅   | ✅  |  ✅  |
| Переход по внешней ссылке (поиск, почта, Telegram)                                     |   ❌   | ✅  |  ✅  |
| **Запросы к ресурсам**                                                                 |        |     |      |
| Запрос на внутренний ресурс (`fetch`, `form`, `iframe`, `img`, `audio`, `video` и др.) |   ✅   | ✅  |  ✅  |
| Запрос на внешний ресурс (`iframe`, `img`, `audio`, `video` и др.)                     |   ❌   | ❌  |  ✅  |
| **Запрос `FORM` на внешний ресурс**                                                    |        |     |      |
| Отправка формы методом `GET`                                                           |   ❌   | ✅  |  ✅  |
| Отправка формы методом `POST`                                                          |   ❌   | ❌  |  ✅  |
| **Запрос `fetch()` на внешний ресурс**                                                 |        |     |      |
| `credentials: "omit"`                                                                  |   ❌   | ❌  |  ❌  |
| `credentials: "same-origin"`                                                           |   ❌   | ❌  |  ❌  |
| `credentials: "include"`                                                               |   ❌   | ❌  |  ✅  |

## Cookies и LocalStorage

| Cookies                                 | LocalStorage                       |
| --------------------------------------- | ---------------------------------- |
| автоматически отправляются серверу      | доступны только на клиенте         |
| размер около 4 КБ                       | обычно 5–10 МБ                     |
| поддерживают `HttpOnly`                 | `HttpOnly` отсутствует             |
| поддерживают Domain, Path, SameSite     | подобных ограничений нет           |
| используются для хранения данных сессии | используются для клиентских данных |

## Частые ошибки

❌ Считать, что Cookies отправляются с каждым HTTP-запросом.

На самом деле браузер учитывает Domain, Path, Secure и SameSite.

❌ Считать, что Cookies — это аналог LocalStorage.

Главная особенность Cookies — автоматическое участие в HTTP-запросах.

❌ Думать, что HttpOnly запрещает отправку Cookie на сервер.

Он запрещает только доступ из JavaScript.

Браузер продолжает автоматически отправлять такую Cookie.

❌ Считать, что SameSite=None достаточно для работы кросс-сайтового `fetch`.

Для AJAX-запросов дополнительно требуется `credentials: "include"` на клиенте и корректная настройка CORS на сервере.

❌ Путать понятия **site** и **domain**.

Правила `SameSite` основаны на понятии **site** (схема + регистрируемый домен), а не только доменного имени.
