# Feature-Sliced Design (FSD)

**Feature-Sliced Design (FSD)** — это архитектурная методология для frontend-приложений, цель которой — разделить код по зонам ответственности и уменьшить связанность между частями приложения.

Главная идея FSD:

> Каждый слой знает только то, что ему действительно необходимо.

Чем выше слой, тем больше он знает о приложении и бизнес-логике.

# Слои FSD

| Слой         | Что хранит                               | Примеры                                    |
| ------------ | ---------------------------------------- | ------------------------------------------ |
| **app**      | Запуск и настройка приложения            | Router, Providers, Store, глобальные стили |
| **pages**    | Готовые страницы                         | HomePage, UsersPage, ProductPage           |
| **widgets**  | Крупные независимые блоки страницы       | Header, Sidebar, UsersTable, Toolbar       |
| **features** | Пользовательские сценарии (действия)     | Login, CreateUser, EditUser, DeleteUser    |
| **entities** | Бизнес-сущности                          | User, Product, Order                       |
| **shared**   | Переиспользуемые вещи без знания бизнеса | Button, Modal, Input, axios, theme, utils  |

> В FSD зависимости направлены сверху вниз. Например, `pages` может использовать `widgets`, а `widgets` — `features`, но не наоборот.

# Пример

Представим страницу со списком пользователей.

На странице есть:

- таблица;
- тулбар;
- поиск;
- фильтр по статусу;
- кнопки «Добавить», «Редактировать», «Удалить»;
- модальное окно создания пользователя;
- иконки статусов;
- меню действий строки.

Разложим всё по слоям.

# shared

Здесь находятся компоненты, **не знающие ничего о бизнес-логике**.

Например:

- Button;
- Input;
- Select;
- Modal;
- Table;
- Tooltip;
- Spinner;
- axios;
- API-клиент;
- UI Kit;
- тема приложения;
- утилиты и хелперы.

Если используется сторонняя UI-библиотека (например, Ant Design или MUI), то в `shared` обычно создают собственные компоненты-обертки с единым стилем приложения.

Например:

```text
shared/ui/Button
shared/ui/Input
shared/ui/Modal
```

# entities

Здесь располагается всё, что относится к конкретной бизнес-сущности.

Например, для сущности User:

```text
entities/user
```

Внутри могут находиться:

- типы пользователя;
- API пользователя;
- отображение статуса;
- Avatar пользователя;
- бейдж статуса;
- карточка пользователя;
- tooltip пользователя;
- меню действий пользователя.

Например:

```text
<UserStatus />

<UserAvatar />

<UserTooltip />

<UserActions />
```

Главное правило:

> Entity описывает объект предметной области, а не действие над ним.

# features

Feature — это законченное действие пользователя.

Например:

- Создать пользователя;
- Редактировать пользователя;
- Удалить пользователя;
- Поиск пользователей;
- Изменить статус пользователя.

Можно представить Feature как ответ на вопрос:

> Что пользователь хочет сделать?

Например:

```text
features/create-user

features/edit-user

features/delete-user

features/search-users
```

Внутри Feature уже может использоваться Entity.

Например:

```text
EditUserModal

↓

UserForm

↓

User API
```

# widgets

Widget — это крупный самостоятельный блок страницы, объединяющий несколько Features и Entities.

В нашем примере это могут быть:

```text
UsersToolbar

UsersTable
```

Например:

`UsersToolbar` объединяет:

- кнопку "Добавить";
- поиск;
- фильтр;
- сортировку.

А `UsersTable` объединяет:

- таблицу;
- статус пользователя;
- меню действий;
- пагинацию.

Widget уже знает, как собрать эти части вместе, но еще не является страницей.

# pages

Page объединяет Widgets в готовый экран.

Например:

```text
UsersPage

├── UsersToolbar
└── UsersTable
```

Именно Page соответствует маршруту приложения.

Например:

```text
/users

/products

/orders
```

# app

Самый верхний слой.

Здесь находится инфраструктура приложения:

- Router;
- Redux Store;
- QueryClient;
- ThemeProvider;
- i18n;
- глобальные стили;
- точка входа приложения.

Например:

```text
App

├── Router
├── Providers
├── Store
└── Theme
```

# Как определить нужный слой

Можно задавать себе несколько вопросов.

**Не знает ничего о бизнесе?**

→ `shared`

**Описывает конкретную бизнес-сущность?**

→ `entities`

**Это действие пользователя?**

→ `features`

**Собирает несколько Features и Entities в один крупный блок?**

→ `widgets`

**Это готовая страница приложения?**

→ `pages`

**Настраивает всё приложение целиком?**

→ `app`

# Частые ошибки

❌ Складывать всё в `shared`.

Если компонент знает о бизнес-сущности (User, Product, Order), ему не место в `shared`.

---

❌ Помещать CRUD-операции в `entities`.

Создание, редактирование и удаление — это действия пользователя, поэтому они относятся к `features`.

---

❌ Делать `widgets` страницами.

Widget — это самостоятельный крупный блок интерфейса, но не весь экран.

---

❌ Делить код только по размеру компонентов.

FSD делит проект **по ответственности**, а не по количеству строк кода или вложенности компонентов.
