# Принципы проектирования

При проектировании приложений существует несколько групп рекомендаций, каждая из которых решает свою задачу.

Можно условно разделить их на четыре группы:

- **SOLID** — принципы объектно-ориентированного проектирования;
- **GRASP** — принципы распределения ответственности между объектами;
- **GoF (Gang of Four)** — каталог паттернов проектирования;
- **KISS, DRY, YAGNI** — общие инженерные принципы разработки.

> Важно понимать, что это не строгие правила, а рекомендации, которые помогают писать более поддерживаемый, расширяемый и понятный код.

# SOLID

**SOLID** — это пять принципов объектно-ориентированного проектирования.

## S — Single Responsibility Principle (SRP)

**Принцип единственной ответственности.**

Каждый класс или модуль должен иметь только **одну причину для изменения**, то есть отвечать за одну конкретную задачу.

### Пример

Сервис отправки писем не должен одновременно:

- отправлять email;
- сохранять пользователей в базу данных.

## O — Open/Closed Principle (OCP)

**Принцип открытости/закрытости.**

Класс должен быть:

- **открыт для расширения**;
- **закрыт для изменения**.

Новую функциональность желательно добавлять без изменения уже существующего кода.

Обычно это достигается с помощью:

- полиморфизма;
- композиции;
- наследования.

## L — Liskov Substitution Principle (LSP)

**Принцип подстановки Барбары Лисков.**

Объекты дочернего класса должны полностью заменять объекты базового класса без нарушения логики программы.

Если после подстановки наследника поведение становится некорректным — принцип нарушен.

### Классический пример

Квадрат не является хорошим наследником прямоугольника, если изменение ширины автоматически меняет высоту.

## I — Interface Segregation Principle (ISP)

**Принцип разделения интерфейсов.**

Лучше иметь несколько небольших специализированных интерфейсов, чем один универсальный.

Класс должен зависеть только от тех методов, которые действительно использует.

Это уменьшает связанность компонентов.

## D — Dependency Inversion Principle (DIP)

**Принцип инверсии зависимостей.**

Высокоуровневые модули не должны зависеть от низкоуровневых.

Оба должны зависеть от **абстракций**.

### Пример

Вместо жесткой зависимости от `fetch` можно использовать интерфейс HTTP-клиента и подставить любую реализацию:

- Fetch API;
- Axios;
- XMLHttpRequest;
- WebSocket (если транспорт построен поверх него).

# GRASP

**GRASP (General Responsibility Assignment Software Patterns)** — набор принципов, описывающих, как правильно распределять ответственность между объектами.

На практике они встречаются реже, чем SOLID, но многие современные архитектуры во многом основаны именно на этих идеях.

## Information Expert

Ответственность должна находиться там, где уже есть необходимые данные.

Если объект обладает всей информацией для выполнения операции — именно он и должен выполнять эту операцию.

## Creator

Создавать объект должен тот класс, который:

- агрегирует его;
- содержит его;
- активно использует его;
- обладает всей необходимой информацией для создания.

## Controller

Вводится объект, который принимает запросы извне и координирует выполнение бизнес-логики.

### Примеры

Backend:

- Controller.

Frontend:

- Store;
- ViewModel;
- Presenter.

(В зависимости от выбранной архитектуры.)

## Low Coupling

**Низкая связанность.**

Компоненты должны как можно меньше зависеть друг от друга.

Это облегчает:

- тестирование;
- поддержку;
- повторное использование.

## High Cohesion

**Высокая связность.**

Каждый класс должен выполнять одну логически связанную задачу.

Обычно высокая связность сочетается с низкой связанностью.

## Polymorphism

Если поведение зависит от типа объекта, лучше использовать полиморфизм, чем длинные цепочки:

- `if`;
- `else`;
- `switch`.

## Indirection

**Посредник между компонентами.**

Вместо прямой зависимости вводится промежуточный слой.

Например:

```text
Приложение
      │
      ▼
MapService
      │
      ▼
 Leaflet
```

Позже можно заменить Leaflet на OpenLayers или Яндекс Карты, не изменяя остальной код приложения.

# GoF (Gang of Four)

GoF — классический каталог из **23 паттернов проектирования**.

Они делятся на три группы:

- порождающие (Creational);
- структурные (Structural);
- поведенческие (Behavioral).

# Порождающие паттерны (Creational)

Отвечают за создание объектов.

## Singleton

Гарантирует существование только одного экземпляра класса.

### Примеры

- Logger;
- Configuration;
- Global Cache.

## Factory Method

Инкапсулирует создание объектов.

Вместо прямого вызова конструктора используется фабрика.

### Пример

Фабрика создания различных типов маркеров на карте.

## Abstract Factory

Создает семейства связанных объектов.

### Пример

Приложение поддерживает несколько UI-библиотек:

- Material UI;
- Ant Design;
- PrimeReact.

Каждая фабрика создает полный набор совместимых компонентов.

# Структурные паттерны (Structural)

Отвечают за организацию взаимодействия между объектами.

## Adapter

Преобразует один интерфейс в другой.

Позволяет использовать несовместимые классы совместно.

## Facade

Предоставляет единый простой интерфейс к сложной подсистеме.

Например:

```text
Table
 ├── Header
 ├── Body
 ├── Footer
 ├── Pagination
 ├── Sorting
 └── Selection
```

Внешний код взаимодействует только с `Table`.

## Decorator

Позволяет динамически расширять поведение объекта, сохраняя его интерфейс.

### Примеры

- логирование;
- кэширование;
- валидация;
- измерение производительности.

В отличие от наследования, декораторы можно свободно комбинировать.

## Proxy

Предоставляет объект-заместитель, который контролирует доступ к настоящему объекту.

### Используется для

- ленивой инициализации;
- контроля доступа;
- удаленного взаимодействия;
- кэширования.

Главная идея Proxy — именно **контроль доступа к объекту**, а не просто выполнение дополнительной логики.

# Поведенческие паттерны (Behavioral)

Определяют взаимодействие между объектами.

## Strategy

Инкапсулирует несколько взаимозаменяемых алгоритмов.

### Пример

```text
ExportStrategy
      │
 ├──────────┬──────────┐
 ▼          ▼          ▼
PDF      Excel       CSV
```

Клиент выбирает нужную стратегию, не изменяя основной код.

## State

Позволяет объекту изменять свое поведение в зависимости от внутреннего состояния.

### Пример

```text
Loading
    ↓
Success
    ↓
Error
```

Каждое состояние имеет собственную реализацию поведения.

# KISS

**Keep It Simple, Stupid.**

Не стоит усложнять архитектуру без необходимости.

Лучшее решение — обычно самое простое.

# DRY

**Don't Repeat Yourself.**

Не следует дублировать знания (**knowledge**) в нескольких местах системы.

Если одна и та же бизнес-логика повторяется несколько раз, ее стоит вынести в отдельную абстракцию.

> Важно: DRY говорит именно о дублировании знаний, а не одинаковых строк кода. Иногда небольшое повторение делает код понятнее, чем чрезмерная абстракция.

# YAGNI

**You Aren't Gonna Need It.**

Не следует реализовывать функциональность "на будущее".

Добавлять стоит только то, что действительно требуется сейчас.

# Частые ошибки

❌ Считать, что SOLID — обязательные правила.

Это рекомендации, которые помогают строить гибкую архитектуру, но не являются догмой.

---

❌ Путать SRP и High Cohesion.

SRP говорит о **единственной причине изменения**, а High Cohesion — о логической связанности обязанностей внутри класса.

---

❌ Считать, что DRY запрещает любое повторение кода.

DRY направлен на устранение **дублирования знаний**, а не одинаковых строк.

---

❌ Использовать паттерны без необходимости.

Паттерны проектирования решают конкретные проблемы. Их применение "ради красоты" часто только усложняет код.
