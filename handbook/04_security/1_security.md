# Безопасность веб-приложений

При разработке веб-приложений важно учитывать не только функциональность, но и безопасность.

Большинство атак направлены на одну из трех целей:

- выполнение произвольного JavaScript-кода;
- выполнение действий от имени пользователя;
- кражу или перехват пользовательских данных.

Наиболее распространенные атаки:

- XSS (Cross-Site Scripting);
- CSRF (Cross-Site Request Forgery);
- Man-in-the-Middle (MITM);
- Clickjacking.

## XSS (Cross-Site Scripting)

XSS — это атака, при которой злоумышленник добивается выполнения произвольного JavaScript-кода в браузере другого пользователя.

Последствия могут быть разными:

- кража данных;
- выполнение запросов от имени пользователя;
- изменение содержимого страницы;
- получение доступа к токенам, если они доступны из JavaScript.

### Виды XSS

#### Stored XSS

Вредоносный код сохраняется на сервере (например, в комментариях, сообщениях или профиле пользователя).

При открытии страницы другими пользователями этот код автоматически выполняется.

Это наиболее опасный вид XSS.

#### Reflected XSS

Код не сохраняется на сервере.

Он передается через URL или форму и сразу возвращается сервером в HTML-ответе.

Часто используется через специально подготовленные ссылки.

#### DOM-based XSS

Полностью происходит на стороне клиента.

Сервер в атаке не участвует.

Например:

```javascript
element.innerHTML = location.search;
```

или

```javascript
eval(userInput);
```

Если пользовательские данные попадают в опасные DOM API без обработки, злоумышленник может выполнить произвольный JavaScript.

### Защита от XSS

Основные способы защиты:

- экранирование пользовательского ввода;
- использование безопасных API (`textContent`, `createElement`);
- отказ от `innerHTML`, если это возможно;
- отказ от `eval()` и подобных функций;
- использование Content Security Policy (CSP).

В React большинство XSS предотвращается автоматически, поскольку JSX экранирует пользовательские данные.

Основная опасность возникает при использовании `dangerouslySetInnerHTML`.

## Content Security Policy (CSP)

CSP — дополнительный механизм безопасности, ограничивающий выполнение JavaScript и загрузку ресурсов.

Политика задается через HTTP-заголовок или `<meta>`-тег.

CSP позволяет:

- запретить inline-скрипты;
- ограничить загрузку скриптов доверенными источниками;
- запретить использование `eval()`;
- ограничить загрузку изображений, шрифтов, воркеров и других ресурсов.

Для разрешения отдельных скриптов могут использоваться `nonce` или `hash`.

Важно понимать, что CSP **не предотвращает появление XSS**, а ограничивает возможности злоумышленника, если инъекция все же произошла.

## CSRF (Cross-Site Request Forgery)

CSRF — это атака, при которой злоумышленник заставляет браузер пользователя выполнить запрос к сайту, где пользователь уже авторизован.

При этом злоумышленник не получает доступ к данным пользователя, а использует его браузер для выполнения действий от его имени.

Например:

- перевод денег;
- смена пароля;
- удаление аккаунта;
- изменение настроек профиля.

Причина заключается в том, что браузер может автоматически прикреплять Cookies к запросу.

### Защита от CSRF

Основные способы защиты:

- использование `SameSite` для Cookies;
- CSRF-токены;
- проверка заголовков `Origin` или `Referer`.

CSRF-токен — случайное значение, которое сервер выдает клиенту и ожидает получить обратно при выполнении защищенных операций.

Даже если злоумышленник заставит браузер отправить запрос, корректный токен он подделать не сможет.

---

## Access Token и Refresh Token

Распространенная схема авторизации использует два токена.

### Refresh Token

Обычно хранится в `HttpOnly Cookie`.

Дополнительно рекомендуется использовать:

- `Secure`;
- `SameSite`;
- `Path`.

Такой токен недоступен из JavaScript даже при успешной XSS-атаке.

### Access Token

Имеет небольшой срок жизни.

Чаще всего хранится:

- в памяти приложения (предпочтительный вариант);
- иногда в `sessionStorage` или `localStorage`.

Используется для авторизации запросов.

Даже если Access Token будет украден, срок его действия обычно невелик.

## Man-in-the-Middle (MITM)

MITM — атака, при которой злоумышленник пытается перехватить или изменить сетевой трафик между клиентом и сервером.

Например, это может произойти в небезопасной публичной Wi-Fi-сети.

Основная защита — использование HTTPS (TLS).

TLS обеспечивает:

- шифрование данных;
- проверку подлинности сервера;
- контроль целостности передаваемой информации.

Важно понимать, что именно TLS защищает от MITM.

Пара Access Token / Refresh Token решает другую задачу — уменьшает последствия компрометации токенов.

---

## Clickjacking

Clickjacking — атака, при которой злоумышленник размещает прозрачный `iframe` поверх своего сайта.

Пользователь думает, что взаимодействует с одной страницей, но фактически нажимает элементы другого сайта, где уже авторизован.

Например, может быть выполнено:

- подтверждение перевода;
- изменение настроек;
- оформление подписки.

### Защита от Clickjacking

Основные способы защиты:

- заголовок `X-Frame-Options` (`DENY` или `SAMEORIGIN`);
- директива `frame-ancestors` в CSP (современный способ).

Они запрещают встраивание страницы в `iframe` на сторонних сайтах.

---

# Сравнение основных атак

| Атака        | Цель                                          | Основная защита                                |
| ------------ | --------------------------------------------- | ---------------------------------------------- |
| XSS          | Выполнение JavaScript в браузере пользователя | Экранирование данных, безопасные DOM API, CSP  |
| CSRF         | Выполнение действий от имени пользователя     | SameSite, CSRF-токены, проверка Origin/Referer |
| MITM         | Перехват или изменение трафика                | HTTPS (TLS)                                    |
| Clickjacking | Обман пользователя через скрытый iframe       | X-Frame-Options, CSP (`frame-ancestors`)       |

# Частые ошибки

❌ Считать, что XSS — это только вставка тега `<script>`.

Выполнение JavaScript возможно множеством способов: через обработчики событий (`onerror`, `onclick`), `javascript:`-URL, небезопасные DOM API и другие механизмы.

❌ Думать, что React полностью защищает от XSS.

React экранирует значения в JSX, но защита исчезает при использовании `dangerouslySetInnerHTML` или небезопасной обработке HTML.

❌ Считать, что `HttpOnly` защищает от CSRF.

`HttpOnly` запрещает чтение Cookie из JavaScript, но не препятствует их автоматической отправке браузером.

❌ Думать, что Access Token и Refresh Token защищают от MITM.

От MITM защищает TLS. Токены лишь уменьшают последствия их возможной компрометации.

❌ Считать, что CSP предотвращает XSS.

CSP не устраняет уязвимость, а ограничивает последствия успешной XSS-атаки.

---

# Что важно запомнить

- **XSS** — выполнение чужого JavaScript в браузере пользователя.
- **CSRF** — выполнение действий от имени пользователя за счет автоматически отправляемых Cookies.
- **MITM** — попытка перехватить или изменить сетевой трафик; основная защита — HTTPS (TLS).
- **Clickjacking** — обман пользователя через скрытый `iframe`.
- Надежная защита строится на сочетании нескольких механизмов: HTTPS, безопасной обработки данных, CSP, `HttpOnly`, `SameSite` и CSRF-токенов.
